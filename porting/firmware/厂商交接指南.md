## 0. 方案总览(决策树)

| 方案 | 内容 | 前提 | 状态 |
|---|---|---|---|
| **A(主选)** | 我们自编 wpk(K 包: G 底座+修补版 xt-clang dcore) | 无 | **已就绪待刷** |
| **B(量产路径/主备选)** | 厂商 SDK + 我们的源码,厂商 xt-clang 全量编译 | 厂商常规构建流程 | 材料齐(§2-§4) |
| **B-nn(B 的性能版)** | 同 B,算法文件换 `silero_vad_nn.c`(NNLib SIMD) | 同 B + nnlib 源(§5) | 材料齐 |
| **C(ELF 代编,最轻)** | 厂商只替换 BUILT_DCORE 为我们的 dcore ELF + 改分区重编 acore/bcore | 底座 SDK 与 ai.recorder 同源(§6) | 有跨核兼容风险 |

K 包若一次通过,A 即终点,B 是量产必经(生产固件本来就在厂商环境编)。
K 包若失败,B 是首选备选——**并且厂商环境不受我们踩过的打包 bug 影响**(见 §7)。

## 1. 为什么集成面这么小(原理,给厂商背景)

原厂 VAD = 闭源静态库 `libwq_sw_vad.a`,对外只有 5 个函数(头文件
`lib/wq_sw_vad/inc/wq_sw_vad.h`):

```c
uint32_t wq_get_sw_vad_hd_size(void);
uint32_t wq_get_sw_vad_scratch_size(void);
void    *wq_sw_vad_init(void *hd, void *scratch, ...);
uint32_t wq_sw_vad_process(void *hd, const short *pcm, int samples, ...);
const char *wq_lib_version(void);
```

Silero 实现按同签名替换这 5 个函数,**processor 层(vad_stream.c/sw_vad.c 的
迟滞/预滚/回调)零改动**——probe 分配、run 喂数、事件上报全部走原厂逻辑。
320 样本/帧进 process,函数内部攒到 512 样本窗再推理(320×8=5×512),对齐
Silero v4 的输入约定。上层应用(app_customer_vad 的 BLE 0x09FF 上报等)无感知。

## 2. 方案 B 操作步骤(普通版,纯 C99 float)

### ① 拷文件(2 分钟)

从仓库 `porting/firmware/` 取,放入厂商 SDK:

| 仓库文件 | 放到 SDK |
|---|---|
| `silero_vad.c`(网络实现) | `components/audio_algorithm/processor/src/` |
| `silero_vad_weights.c`(601KB 权重,2.1MB 源码) | 同上 |
| `wq_silero_vad.c`(5 函数封装+攒帧) | 同上 |
| `silero_vad.h` `silero_vad_consts.h` | `processor/inc/` |
| `wq_silero_vad.h` `wq_sw_vad.h`(接口声明) | 同上 |
| (可选,DVT 用)`integration/hil/wq_silero_hil.c` + `silero_hil_audio.h` | 同 src/;挂钩点 `apps/dcore/entry/entry.c` 的 `app_main_entry` 尾部 |

权重文件 `gen_weights.py` 可从 ONNX 再生,不必手改。

### ② 挪库(1 分钟,可回退)

`lib/wq_sw_vad/` 整目录移出 `lib/`(如 `lib_disabled/`)。
移回 = 回退原厂 WebRTC VAD。

### ③ 配置(3 处)

1. **defconfig**:在厂商**自己的** defconfig 上加 `CONFIG_VAD_ENABLE=y`;
   工具链保持 `CONFIG_XT_TOOLCHAIN_XT_CLANG=y` 不动。
   (仓库里的 `defconfig.silero` 是我们 GCC 联调专用,**不要**给厂商用)
2. **flash_layout**(工程下 flash_layout.h 的 JSON):`dcore image` 分区
   `sectors: 300 → 400`(权重进镜像后 dcore ≈1.43MB)。
   **全量重编时 acore/bcore 会被构建系统自动重链到新位置,无需手工干预。**
3. **`wq_gcc_shim.c` 必须保留**(xt-clang 构建同样需要! 2026-10-08 实证: xt-clang 对 float 除法发射 `__recipsf2` 调用,经 `-Wl,--just-symbols=rom_image.sym` 解析到 ROM 0x2615f300 会永久死机——shim 的自带实现是必需品);xtensa_tools.py 的 -Wno-error
   豁免都是我们无 license 的 GCC 环境专用,xt-clang 下不需要(带上也无害,
   但建议干净)。

### ④ 编译+自检

厂商常规 `scons --defconfig=... && scons -j16`。编完两条自检:

```bash
# dcore ELF 里应有(符号验证):
xt-nm glass_dcore.elf | grep -E "sv_process|wq_sw_vad_process"   # 有符号
xt-nm glass_dcore.elf | grep -c WebRtcVad                          # = 0(原厂库已剔除)
```

以及(强烈建议,10 秒): `python3 validate_dcore.py <wpk里的glass_dcore.bin>`
(仓库 `porting/firmware/integration/validate_dcore.py`,校验镜像段表链完整性,
背景见 §7)。

## 3. 验收协议(交付判定,三关)

1. **数值关(HIL 自环)**:固件上电自动跑 40 窗黄金音频,调试串口(7036AC 为
   GPIO_98/93,**2,000,000 8N1**)输出 `[SHIL] begin windows=40` → 40 行
   `win=NN p=X.XXXX` → `end`。日志 txt 发回,我们跑
   `python3 hil_parse.py <日志> golden_prob.f32`,**最大偏差 ≤0.1 验收**
   (PC 基准 vs onnxruntime 逐窗偏差 7.7e-7,固件侧预期 <0.02)。
   xt-clang 版 40 窗应在数秒内跑完。
2. **稳定关**:连续上电 10 次,无 heap_tlsf/WDT/double exception。
3. **性能关(可选,量产建议)**:wq-debug-tools 的 cpu_usage 测 dcore 占用;
   普通版预估标量 FPU 单窗 ~50-100ms(余量充足);NNLib 版 <5ms(§5)。

golden_prob.f32、hil_parse.py、validate_dcore.py 都在仓库 `porting/firmware/`。

## 4. 方案 B 常见问题(我们踩过的,预答)

| 症状 | 原因/处理 |
|---|---|
| `ro_cfg_init read ro cfg error` | 无害,加载默认配置,不影响 VAD;厂商自己的 ro_cfg 保持不动 |
| 链接报 `_Assert/__recipsf2` 未定义 | 那是 GCC 环境缺运行时;xt-clang 自带,不会出现 |
| dcore 放不下(分区溢出) | flash_layout dcore 400 扇区(1.6MB)已够 1.43MB;NNLib 版再大 ~40KB 仍在范围内 |
| 上电无 [SHIL] | 检查接的是日志口(2M)而非烧录口;HIL 钩子被 CONFIG 裁掉;或 §7 的镜像问题 |
| 刷完秒死零日志/几秒后 heap_tlsf | 见 §7——先跑 validate_dcore.py |

## 5. 方案 B-nn:NNLib 加速版(性能版,接口完全相同)

在 §2 之上**只改一处**: `processor/src/silero_vad.c` → 换成仓库
`porting/firmware/nn/silero_vad_nn.c`(原文件改名 silero_vad_ref.c 留档回退)。
其余 11 个集成文件(权重/封装/HIL)全部复用。

需额外拷 NNLib 内核源(来自 XNNC SDK `assets/library/nnlib/`,随 Cadence
XNNC_3.2.2 分发)到 `processor/src/nnlib/`,精确 9 个 .c:

```
src/algo/kernels/cnn/hifi5/xa_nn_conv1d_std_f32.c         (STFT, 80% 热点)
src/algo/kernels/matXvec/hifi5/xa_nn_matmul_f32.c          (1x1 卷积)
src/algo/kernels/matXvec/hifi5/xa_nn_matXvec_f32.c         (LSTM 门)
src/algo/kernels/matXvec/hifi5/xa_nn_dot_prod_f32.c        (decoder FC)
src/algo/kernels/activations/hifi5/xa_nn_activations_f32_f32.c
src/algo/kernels/basic/hifi5/xa_nn_elm_add_f32.c           (残差)
src/algo/ndsp/hifi5/src/vec_sigmoidf_hifi5.c
src/algo/ndsp/hifi5/src/vec_tanhf_hifi5.c
src/algo/ndsp/hifi5/src/vec_reluf_hifi5.c
```

编译参数加 include 路径:

```
-I<nnlib>/src/include
-I<nnlib>/src/algo/common/include
-I<nnlib>/src/algo/ndsp/hifi5/include
-I<wq_hifi5_asic>/src/cstub        (xtensa/tie/xt_hifi*.h 所在)
```

全程 f32 零量化,数值与参考实现一致(1e-5 量级),验收协议同 §3。
注意:`xa_nn_sigmoid_32_32/xa_nn_tanh_32_32` 是定点 Q 格式**不要用**,
激活必须走 `xa_nn_sigmoid_f32_f32/xa_nn_tanh_f32_f32`。

## 6. 方案 C:ELF 代编(最轻,但有前提)

若厂商不想集成源码:把我们编好的 `glass_dcore.elf`(xt-clang 产物)给他们,
他们 (1) flash_layout dcore 300→400, (2) 用我们的 ELF 替代 BUILT_DCORE,
(3) 重编 acore/bcore 并打包。**为什么必须重编 acore**:acore/bcore 是 XIP
执行,链接地址=flash 位置(0x34000000+lma+0x20),dcore 扩分区会推移 acore
位置,不重链就是执行垃圾(I 包实证)。
**风险**:我们的 dcore 基于 ai.recorder SDK,与厂商版本 acore 的核间
RPC/IPC 协议兼容性未验证(K 包用同源底座回避了此问题)。所以 C 只在
厂商底座与 ai.recorder 同源时推荐,否则选 B。

## 7. ⚠️ 公开版 SDK 打包 bug(重要,请转告固件团队)

2026-09-30 实证:公开链路(wq-toolchain-dl 的 wqcore)的打包工具
`tools/SCons/xtensa_tools.py` `combine_sections()` 有 bug——cache 段
(vma 0x26200000)对齐补零用 `bytes.zfill()`,**补零长度被计入段 len**,
而加载器按 `off+len` 链式定位下一表项 → dcore 镜像最后一个段表项
(`.clib.data+.dram.data`)被错读成数据 → **DSP 初始化数据永不加载**,
症状随 RAM 残留内容漂移(秒死零日志 / 数秒后 heap_tlsf / WDT),
极难定位。对照:贵司 v0.7.2.8 / v0.9.2.8 官方镜像段表链均完整
(len 不含补零),即**内部版本无此 bug;若从公开版 SDK 自建固件请检查**。

- 自查: `python3 validate_dcore.py glass_dcore.bin`(PASS/FAIL 一目了然)
- 修复(若用公开版): `xtensa_tools.py` combine_sections 中
  `s['data'].zfill(...)`/`s['len']=len(s['data'])` 改为
  `s['data'] = b'\x00' * (s['offset']-offset) + s['data']`(len 保持内容长)。
  已编好的镜像也可 4 字节修补(xt-clang 版 @0xc6684: 0x99bcc→0x99b74)。
