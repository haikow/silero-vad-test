# WQ7036AC Silero VAD 移植 · 踩坑总结(2026-09-20 ~ 10-08)

> 两个多月、A→T 共 19 个固件包的实战复盘。按"工具链 / license / 基线 / 镜像打包 /
> 调试方法"五类归档, 每条给出症状→根因→解法。**最大的教训放在最前面。**

---

## 〇、总纲: 最大的坑是"基线错配"(其余坑的一半受害者)

**症状**: 自编固件上板永远 `rpc_service.c:424 Asserted!` → double exception → 复位循环;
dcore/bcore 零日志; 换了 dcore 编译器/镜像修补/RPC 耐心/换 sbl 全部无效。

**根因**: 目标板实为 **glass-stereo-dac 产品线(ADK 1.4.0.69, 厂方 v0.9.2.8 固件可稳定启动)**,
而我们全部 A~Q 包建在 **ai.recorder 示例(ADK 1.3.0.398, 更旧一代)** 上。两套 ADK 的
Flash 分区表、ro_cfg、acore VMA、FOTA 布局、核间兼容性**全部不同**——在错地基上做的
任何 dcore 层修复都不可能生效。

**发现路径**(逆向贡献决定性): 工作包 wpk 的 `dbglog_table.txt` 反推出 146 个源文件清单
(含 ai.recorder 没有的 app_record/it8563/icp1206)→ 产品线身份确认; 用户核对
FW-VERSION/ADK 版本实锤; 用 `wq-audio_1.4.0.69` 源包 + 工作包 ro_cfg 复现基线(S 包三核全活)。

**教训**:
1. 上板前必须回答"这块板的原厂固件是哪个工程编出来的", **对照组要同代同源**;
2. "能启动的官方包"是最好的 oracle——先做**字节级/结构级 diff**(分区表/符号/文件清单), 再谈行为;
3. 跨产品线拼包(ai.recorder 的 dcore + 别的底座)注定 rpc 断言循环。

## 一、工具链坑

| # | 坑 | 症状 | 根因/解法 |
|---|---|---|---|
| 1 | GCC 编 SDK 不能上实时 | A/B 包 WDT 超时, 单窗推理数百 ms | xtensa-wuqi-elf-gcc 12.2 是**软浮点**构建(不用 HiFi5 FPU); 仅够功能验证。生产必须 xt-clang |
| 2 | GCC 与 XCC 预编译库混链 | heap_tlsf 断言 / _Assert 死循环 | SDK 70+ 预编译库是 XCC 编的: GCC 缺 `_Assert/__recipsf2/__ieee754_sqrtf`(需垫片 wq_gcc_shim.c); GCC 任务栈比 XCC 大 10-30% → 溢出踩堆。A~G 包崩溃的成分之一 |
| 3 | xt-xcc 不能用 | 链接报 "dangerous relocation" | xcc 的 literal 布局问题; **必须 xt-clang**(defconfig `CONFIG_XT_TOOLCHAIN_XT_CLANG=y`) |
| 4 | XtensaTools 版本敏感 | 同 MD5 的公开版编译报 license 错 | 必须用**方案商发的那份**(注册表/配置路径不同); 注册表指向 /opt/xtensa/XtDevTools/install/{tools,builds}/RI-2020.4-linux/, 容器内要按此布局放置 |
| 5 | RISC-V 工具链版本随 ADK 变 | 1.4 构建秒退 riscv_tools.py | ADK 1.3 要 GCC 10.2, **1.4 要 GCC 14.2**; 物奇公开 GitLab(222.71.131.187:8888, 项目16 iot/wq-toolchain-dl, ref=master)可下载 |
| 6 | scons 增量构建混产物 | 修了工具脚本但产物不变/半新半旧 | 改打包/链接相关代码后**全清对应核的 build 子目录**再编 |
| 7 | scons 输出接管道会杀构建 | `scons -j16 \| head -8` 后构建中断且无报错 | head 关闭管道→SIGPIPE; 输出重定向到文件再过滤 |
| 8 | 改 defconfig 不生效 | 配置项没编进去 | 改后必须 `scons --defconfig=...` 重新生成 sdkconfig |
| 9 | 1.4 编译警告升级 | `-Werror,-Wmissing-prototypes` 报错 | 函数定义前加前置原型声明 |
| 10 | 1.3 私有宏 | `is_defined(...)` 未定义 | 1.4 环境没有这个 SCons 注入宏, 改标准 `defined()` |
| 11 | xt-clang 拒绝自定义段名 | `cannot use '.icache.literal' in section attribute` | 旧 workaround(7036AX DRAM 溢出时把权重链 icache 区)在 AC/1.4 不需要也不被接受; 置空段属性宏 |
| 12 | Kconfig 选项名有陷阱 | 写 `CONFIG_AUDIO_VAD_ENABLE=y` 不生效 | 总开关是 **`CONFIG_VAD_ENABLE`**(它 select AUDIO_VAD_ENABLE/RECORDSV/RECORD_BASE); 且 `aud_sv_vad.c` 强制要求 `RING_ALLOCATE_CFG=2或3` |

## 二、xt-clang license 坑

| # | 坑 | 症状 | 根因/解法 |
|---|---|---|---|
| 1 | feature 名不匹配 | FlexNet -5,357 No such feature | 公开 RI-2020.4 的 xt-clang 请求 **XTENSA_XCC_TIE**; 方案商 license 发的是新命名 **XT_XCC_TIE_EB043600**(EB043600=Cadence 核配置 Product Variant ID, **不是 MAC**) |
| 2 | 手改 license | FlexNet -8,523 | license 按 feature 行签名, 改名即失效——死路, 别试 |
| 3 | 直读 license 文件全失败 | 穷举 6 种方式同样报错 | **必须走 lmgrd license server**: SERVER/VENDOR 头 + 原 INCREMENT 行拼成 lic.dat, 客户端 `LM_LICENSE_FILE=27000@localhost`——lmgrd 做 feature 名映射 |
| 4 | HOSTID 校验 | server 起来但拒绝 | license 绑 MAC 00155d2b42e6; Docker 必须 `--mac-address 00:15:5d:2b:42:e6` |
| 5 | lmgrd 起不来 | rosetta "failed to open elf" | lmgrd 需要 LSB loader: `ln -sf /lib64/ld-linux-x86-64.so.2 /lib64/ld-lsb-x86-64.so.3`; 另建 /usr/tmp/.flexlm |
| 6 | "license 全工具链通用"说法 | 方案商口头保证 | 实测不通用(ISS/TurboXim 需单独 feature, TurboXim 没有); 以实测为准 |
| 7 | 完整可用配方 | — | Docker(--mac-address)+厂商 XtensaTools+/opt/xtensa 布局+lmgrd+LM_LICENSE_FILE=27000@localhost+XTENSA_SYSTEM=.../XtensaTools/config, 详见移植指南 §9 |

## 三、镜像与打包坑

| # | 坑 | 症状 | 根因/解法 |
|---|---|---|---|
| 1 | **1.3 打包工具 zfill bug** | dcore 零日志秒死或数秒后 heap_tlsf(症状随 RAM 残留漂移) | `xtensa_tools.py` cache 段对齐补零用 `bytes.zfill()` 且**补零计入段 len**, 链式加载器(off+len+16)把末段表项错读成数据 → `.dram.data` 永不加载。官方镜像对照实证(其 len 不含补零)。1.3 需修工具或 4 字节补丁; **1.4 已修** |
| 2 | acore/bcore 分区位置不可动 | 挪分区后连 "Boot from" 都不出 | acore/bcore 是 **XIP 执行**(链接地址=0x34000000+flash偏移+0x20), 挪动必须重链; 只有 dcore(整段拷进 DSP RAM)可自由换位 |
| 3 | FACECAFE 容器格式无文档 | — | 16B 头(magic/段数/总长/入口)+**段表项与数据交错**, 逐段 16B(type/off/vma/len); 校验器 `integration/validate_dcore.py` 一键判 PASS/FAIL |
| 4 | **ROM 符号悬空** | xt-clang dcore 零日志永挂, ISS 死于 ROM 调用 | 0x26100000=AUD_S0_TCM_IROM(芯片内置 ROM 库); 符号经 `-Wl,--just-symbols=rom_image`(1.3 为 .sym, 1.4 为 .ld)注入成**绝对符号, 会压制目标文件同名定义**。xt-clang 对 float 除法发射 `__recipsf2`, 解析到从未验证的 ROM 地址即死。解法: 从符号表剥离 → **libgcc.a 自带实现自动顶上**(比手写 shim 对: shim 里的 `1.0f/x` 又会拉 libgcc 除法撞 multiple definition) |
| 5 | ROM 依赖审计 | 换编译器后悬空风险 | 做**符号命中级三方对照**(refs(自己) − refs(官方) − refs(能跑的版本)); 裸 4 字节扫描会被权重数据淹没 |
| 6 | 烧录头/镜像格式 | — | acore/bcore 裸代码, 烧录器补 32B wq_image_header(guard=0xA4E49A17); 分区 id: sbl=16/acore=32/bcore=48/dcore=112/ro_cfg=194/bootmap=8 |

## 四、调试方法坑(与收获)

| # | 坑/方法 | 说明 |
|---|---|---|
| 1 | **ISS 默认起点是坑** | xt-run 默认从核 reset vector(0x26000000 **空区**)起跑=仿真空内存; 必须 `--noreset` 从 ELF 入口起; `--cycle_limit=N --pchistory=K` + 周期二分=PC 逻辑分析仪 |
| 2 | ISS 无 ROM/外设模型 | 死于 ROM 调用(xthal_save_extra_nw 等)≠真机死——GCC/官方也调且能跑即假死; 无 ROM dump 时 ISS 只能定位"到 ROM 边界为止" |
| 3 | 模糊截图 OCR 幻觉 | 曾从截图"读出"不存在的 win=0~2 数据; **日志一律要 txt 原件** |
| 4 | 一次换太多变量 | H 包换工具链全量重编(acore/bcore/dcore 全变), 崩了无法归因; 后续改用"已知好底座+单换一核+4字节二进制补丁"的外科手术式实验(J/K/M 包), 每次烧录换一个确定结论 |
| 5 | 零日志死亡的最后手段 | 面包屑(裸 UART 直写里程碑字母)+异常现场裸打印(向量汇编里把 EXCCAUSE/EPC/EXCVADDR 打成 `Q..e..p..v`)——不依赖任何初始化; sbl 横幅证明裸 UART 通道可用 |
| 6 | 金标准对拍 | 段表链校验器、符号对照、dbglog 文件清单反推——**结构级 diff 优于行为级**; `--just-symbols` 绝对符号会压目标文件定义, 出问题先查它 |
| 7 | 汇编对齐 | Xtensa 函数标签必须逐个 `.align 4`, 否则 "call target must be 4-byte aligned" |
| 8 | 烧录/串口 | 进下载模式=上电 GPIO_101 高; 烧录口 GPIO_01/02(XMODEM 2M 起手); 7036AC 日志口 GPIO_98/93 2M 8N1; 官方工具靠 DTR/RTS 自动复位进下载 |
