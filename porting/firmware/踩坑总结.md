## 〇、总纲: 最大的坑是"基线错配"(其余坑的一半受害者)

**症状**: 自编固件上板永远 `rpc_service.c:424 Asserted!` → double exception → 复位循环;
dcore/bcore 零日志; 换了 dcore 编译器/镜像修补/RPC 耐心/换 sbl 全部无效。

**根因**: 目标板实为 **glass-stereo-dac 产品线(ADK 1.4.0.69, 厂方 v0.9.2.8 固件可稳定启动)**,
而我们全部 A~Q 包建在 **ai.recorder 示例(ADK 1.3.0.398, 更旧一代)** 上。两套 ADK 的
Flash 分区表、ro_cfg、acore VMA、FOTA 布局、核间兼容性**全部不同**——在错地基上做的
任何 dcore 层修复都不可能生效。

**发现路径**(逆向贡献决定性): 工作包 wpk 的 `dbglog_table.txt` 反推出 146 个源文件清单
(含 ai.recorder 没有的 app_record/it8563/icp1206)→ 产品线身份确认; 用户核对
FW-VERSION/ADK 版本实锤; 用 `wq-audio_1.4.0.69` 源包 + 工作包 ro_cfg 复现基线(S 包三核全活)。

**教训**:
1. 上板前必须回答"这块板的原厂固件是哪个工程编出来的", **对照组要同代同源**;
2. "能启动的官方包"是最好的 oracle——先做**字节级/结构级 diff**(分区表/符号/文件清单), 再谈行为;
3. 跨产品线拼包(ai.recorder 的 dcore + 别的底座)注定 rpc 断言循环。

## 五、数值精度与参数坑(2026-10-09 ~ 10-10, T→JJ 包)

> 数值验收从"永远对不齐"到**窗 0-22 全部偏差 ≤0.0001**(II 包实测), 靠的是下面这条
> 根因链: 每一环单看都像"精度问题", 实际全是**确定的 bug**。教训: 浮点偏差大到 0.1
> 量级时, 不要先怀疑"累加顺序/精度", 先怀疑算子语义和参数。

### 5.1 NNLib 布局三连坑(一条主线: HWC 风格布局, ONNX 权重直传必错)

NNLib 是 Cadence 给自家训练框架喂的内核, 输入/权重全按 HWC 风格排布, 且**零输入时
输出=bias=0, bug 完全隐身**——前 20 个包的"验证通过"全是全零输入给的假阴性:

| 内核 | 期望布局 | 我们传的 | 症状 | 修复 |
|---|---|---|---|---|
| `xa_nn_matmul_f32xf32_f32` | 输入 [T][IC](源码 line 91 `p_vec=p_vec1+vec*cols1`) | [IC][T](CHW) | 非零输入读错位权重→act0 全零 | pw1x1/pw1x1_s2 标量化 |
| SDK `.a` 的 elm_add+vec_relu | 不可靠(未查明) | — | pw 修好后 act0 仍全零 | res_relu 标量化(EE 包) |
| `xa_nn_conv1d_std_f32` | kernel 按 [OC][**ICW_pad×KH**] 喂 matXvec_circ_nb, ICW_pad=PADDED_SIZE(IC×IW,**2**) | kernel 当 [OC][KH] 直传 | IC=IW=1→cols=512, 按 [258][512] 读, **oc≥129 越界读后续权重区**(GG 包: 结构性零通道 129 炸出 -47261) | 纯参数重排 [OC][KH=64][ICW=4](input_height 704→176, input_width 1→4, kernel_height 256→64, y_stride 64→16), kernel/输入内存一字节不动(HH 包) |

- 定罪手段: **结构性零**——rFFT 的 DC bin 虚部基是全零行, stft[*][129] 任何输入下恒为 0,
  板上非零=conv1d 必错, 一票否决不用看别的
- conv1d 的 p_scratch 是**环形缓冲不是小结构体**: 需 kernel_height×ICW_pad×4B
  (旧布局 ~2.1KB); 给 384B 时溢出踩邻静态→挂死。现在布局只需 1KB
- 参数检查全过≠布局对: `y_stride≤kernel_height` 等检查都会 PASS, 越界照样发生

### 5.2 参考实现漏 4 个中间 ReLU(II 包修复, 最隐蔽的一环)

- **ONNX 图真相**: 每个残差块是 **dw → ReLU → pw**(张量名 `/dw_conv/dw_conv.1/Relu`),
  first_layer/enc3/enc7/enc11 四处; C 参考实现把 dw 原始输出直接喂 pw, 全漏
- **症状模式**: 静音/过渡窗 p 偏高 0.1-0.39, 语音窗接近(≤0.06)——静音时 dw 输出在零附近,
  ReLU 钳位差异被后级放大; 语音时 dw 大正数, ReLU 无感
- **为何藏了这么久**: "act0 匹配 PC 金标"是 **C-vs-C 循环验证**(金标 dump 来自同款漏法的
  PC 参考链), 不是 C-vs-ONNX。golden_prob.f32 本身是 onnxruntime 直出的, 一直没错,
  错的是中间层的"金标"
- PC 参考实现(firmware-silero/silero_vad.c)的 dwconv5 本就带 `relu=1` 参数且调用点都传了 1
  ——**是移植到 SDK 时把参数丢了**。修复=SDK 版 dwconv5 内嵌 ReLU
- 修复后: numpy 复现窗 0 p=0.0415=onnx 精确一致; PC 参考对 onnx 全 40 窗 **7.7e-7**(窗 23)。
  也顺便证伪了"网络混沌"假设——偏差大必另有 bug

### 5.3 HIL 音频 ×32767 量化 bug(II 包修复, "参数问题"的典型)

- golden 音频本身在 int16 网格上(值=k/32768), HIL 音频头生成器误用 **×32767** →
  每个非零样本朝零偏 1 LSB(k≥1 全变 k-1), 与固件端 `(float)pcm/32768.0f` 不互逆
- **症状**: 板端 stft 比金标一致性偏小 ~0.05%(窗 8: 201959 vs 202093), 静音窗相对误差最大
- **定位手法**: 拿 HIL 头的**真实样本**喂 numpy → 逐位复现板端全部 stft(8/8 窗)→
  一锤定音是输入音频, 不是 conv1d
- 修复: `gen_hil_audio.py` 用 **×32768** 生成, 并断言 `round(x*32768)/32768 == x` 无损
- 排查中证伪的假设(记下来防重蹈): "onnx 对 int16 输入量化敏感"——量化金标与原始金标
  **逐位一致**, 1-LSB 输入噪声根本传不到 p; 所以 p 偏差必是数学 bug, 不是输入表示

### 5.6 性能坑: data_xip 是慢速 flash 窗(JJ 包实验)

- DSP 核**无 I/D cache**(core.xparm: dcacheOption=0/icacheOption=0); flash 经两个窗口:
  `inst_xip`@0x26200000(代码执行, 快)与 `data_xip`@0x34000000(数据, **实测 ~5.5MB/s**)
- 权重 601KB 默认落 data_xip → STFT 每窗流读 2.1MB kernel ≈ **400ms**(II 实测);
  耗时随流量线性(旧 cols=512 时 757ms), 流读实锤
- 阶段耗时(II, 窗0): STFT 400ms / LSTM 80ms / first_layer 49ms / decoder 35ms / enc 23ms
- **JJ 解法**: 权重搬 inst_xip(`section(".xip.text.sv_weights")`, 630KB 空闲装 601KB)+
  pw1x1 k 循环外提(权重每元素只读一次, 加法序不变→数值逐位一致)
- SDK 有 `wq_flash_enable_higher_dummy_cycle`(flash 保守慢速模式)——不要动, 变砖风险
- **JJ 实测翻车**: 以为"代码能从 inst_xip(0x26200000) 执行, 数据放那也能读"——错!
  该窗是 DSP **取指专用**(链接脚本名 inst_xip; loader 源码注释 `// skip icache`;
  加载器只设一个 SFC 偏移寄存器不拷贝)。实测: 段表结构合法、HIL begin 能打印(取指正常),
  但 `pack_all()` 第一次**读**权重(0x2625xxxx)即崩 → dcore 死 → coredump → WDT 50s 循环复位,
  [SVs] 一条不出。段表校验 PASS 完全不能暴露这类问题——**校验器只验容器结构, 不验硬件语义**
- **KK 解法**: 权重回 data_xip; 运行时把 STFT kernel(264KB)一次性 `wq_heap_caps_malloc`
  (MALLOC_CAP_ALIGN_16BYTE) 暂存进 TCM 堆(堆 314KB 装得下), conv1d 传 TCM 指针;
  分配失败回退 flash 指针(慢但正确)。data_tcm.heap 链接期占 314KB, 借用要留余量
