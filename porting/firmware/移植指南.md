> 细节展开见同目录 `integration/README.md`(wq-adk 集成)、`integration/烧录硬件指南.md`(烧录/接线)、

## 0. 成果速览

| 项 | 结果 |
|---|---|
| 替换对象 | 原厂 WebRTC VAD(闭源 `libwq_sw_vad.a`)→ **Silero VAD v4(纯 C99 源码,float)** |
| 数值验证 | C 实现 vs onnxruntime:40 窗最大偏差 **7.7e-7**;攒帧管道纯度 0.0;int16 量化损失 1.7e-2 |
| 固件 | 7036AC 与 7036AX 双芯片 wpk 产出并**实机烧录成功**(2026-09-23) |
| 侵入性 | **processor 层零改动**——复用原厂 VAD 的 5 函数接口,上游(vad_stream/sw_vad)无感知 |
| 资源 | 权重 601KB(链 icache 段) + 静态缓冲 26KB + 句柄 3KB;计算 ~70 万 MAC/窗 |

## 1. 路线定案(为什么这么走)

1. **放弃 NPU**:原厂拒提供 neo params(`wq_hifi5_asic-params` 中 `HasXNNE=0`),XNNC 3.2.2 又有流式
   LSTM 编译 bug(`memref.copy` 崩溃)→ NPU 路线在公开资料边界内不可行。
2. **纯 DSP float C**:HiFi5 有 FPU,Silero 网络很小(~70 万 MAC/32ms 窗),C99 直接写。
3. **接口仿真而非重接**:原厂 VAD 对外就 5 个函数(下表),全部按原签名实现,processor 管线
   (mirror→shaper→sw_vad→kws→breaker)一行不用改:

| 原厂函数 | 我们的实现 |
|---|---|
| `wq_get_sw_vad_hd_size()` | 返回 `sizeof(wq_silero_hd_t)`(3KB) |
| `wq_get_sw_vad_scratch_size()` | 返回静态缓冲需求(26KB) |
| `wq_sw_vad_init(hd, scratch)` | LSTM h/c 状态清零 + STFT 状态复位 |
| `wq_sw_vad_process(hd, pcm)` | **320 样本(20ms)进,内部攒到 512 样本窗**(320×8=5×512)后推理 |
| `wq_get_sw_vad_lib_version()` | 返回 "silero-v4" |

| # | 症状 | 根因 | 解法 |
|---|---|---|---|
| 1 | C 实现概率和 ORT 对不上 | STFT 是 reflect pad(96,96) 出 **8 帧**;归一化减项是全局标量;conv1x1 输入布局 [C][T] | 逐节点转写 + ORT 中间张量 dump 三方对照逐级二分 |

| 4 | dcore 镜像 1.43MB 超分区 | 300 扇区只装 1.17MB | flash_layout dcore→400 |
| 5 | 烧录工具 2 秒报错退出 | **固件编成了 7036AC,板子是 7036AX** | 按实际芯片重编(见 §2.3) |
| 6 | 7036AX 链接 DRAM 溢出 84KB | 623KB 权重 + stereo.dac 代码 > 768KB DRAM | 权重链 `.icache.literal`(1MB 空闲区),`SV_WSEC` 宏实现 |
| 7 | 改段属性后 WebRTC 符号复活 | build 缓存 | 全清重编 |

| 10 | 日志口(GPI040/41 预留串口)零字节 | **Dmic4 导通跳线帽占用复用引脚** + 产线固件可能关日志 | 拔 DMIC4 跳帽;或用母板内置串口(Demo 板 TypeC 直连) |

## 7. 上板首测问题追踪(2026-09-24,7036AC 实测)

**现象**:烧录成功后上电,dcore(DSP)崩溃:WDT2 timeout、exccause=0x1f(NMI)、
`DCORE crash at time 591324`。串口自检输出中断。

**分析**(方案商判断+我方确认):GCC 软浮点版单窗推理耗时远超 WDT 窗口,
自检在开机入口连续跑 40 窗霸占 dcore → 看门狗超时 NMI。次要嫌疑:内存被踩/集成位置。

**对照实验双包**(均在 `~/Desktop/烧录工具箱/`,defconfig 在 integration/config/7036AC/):

| 包 | 改动 | 目的 | 判读 |
|---|---|---|---|
| A包 ai-recorder-stub | `SILERO_STUB=1`:process 跳过推理恒 0,权重被裁(1.62MB) | 隔离"计算耗时"变量 | 不崩=锁死计算耗时;还崩=框架/内存问题 |
| B包 ai-recorder-paced | `SILERO_HIL_PACE_MS=800`:每帧(20ms)前延时 800ms,推理照常(2.14MB) | 让出 dcore 喂狗,完成 40 窗数值验收 | 跑完 40 窗+不崩=WDT 实锤且拿到数值 |

源码开关:wq_silero_vad.c `SILERO_STUB` / wq_silero_hil.c `SILERO_HIL_PACE_MS`(默认 0/0)。
MD5:A=d444ce52aa9fe23d48fb58c4fff03bc7,B=f1c1b959f46aa08aa68f030981860899。

**根治方向**:xt-clang(FPU)版——单窗耗时应缩 20 倍以上,自检+实时管线双解决。

## 8. 上板崩溃完整审计(2026-09-30,A/B/C/D/E/F/G 包诊断系列)

### 崩溃记录

| 包 | VAD | HIL | 崩溃方式 | 关键发现 |
|---|---|---|---|---|
| 原版 | 完整 | 有 | WDT2 超时 + NMI @591ms | dcore 崩在 Opus 编码器(GCC 软浮点拖垮 CPU) |
| B包(paced) | 完整+限速 | 有 | WDT2 超时 + NMI @591ms | 同原版(帧间延时效不了单帧内部耗时) |
| A包(stub) | 置空 | 有 | **heap_tlsf.c:369 断言** @4904ms | 无推理也崩 → 不是计算耗时问题! |
| C包(无VAD) | 无 | 无 | 待测 | 纯 GCC SDK 底座对照 |
| D包(VAD无HIL) | 完整 | 无 | 待测 | 隔离 HIL 自检 |
| G包(修复) | 完整 | 有(延迟3s) | 待测 | scratch 26KB + HIL 延迟 |

### 审计结论(.comment 段实证)

固件混链两种编译器:
- **GCC 12.2.0**(crosstool-NG): SDK 全部源码 + Silero VAD
- **Xtensa Compiler 14.04**(XCC): 70+ 预编译库(xa_nnlib/wq_kws/wq_aec/wq_enc/wq_eq 等)

### 根因分析(按嫌疑排)

| 嫌疑 | 机制 | 验证方法 |
|---|---|---|
| **① GCC 任务栈溢出(最大嫌疑)** | GCC 生成的栈帧/寄存器保存比 XCC 大 10-30%,SDK 任务栈按 XCC 调的 → 溢出踩堆 → heap_tlsf 断言 | 刷 C包(纯 GCC 底座),崩则实锤 |
| ② wq_gcc_shim `_Assert` 死循环 | XCC 库命中 assert → 调我们的 `_Assert` → 死循环 → WDT | B包的 WDT 崩溃模式吻合 |
| ③ GCC/XCC ABI 差异 | 结构体对齐/填充/long double 布局不同 | 需逐接口比对 |
| ④ GCC 软浮点性能 | 单窗 70万 MAC 超看门狗窗口(~590ms) | 原版/B包的 WDT 崩溃模式吻合 |

### wq_gcc_shim.c 风险点

```c
void _Assert(const char *expr, ...) {
    volatile int hang = 1;
    while (hang) {}  // ← 死循环! XCC 库 assert 后系统挂起 → WDT
}
```

建议:改为复位而非死循环:
```c
void _Assert(const char *expr, ...) {
    // 打印后软复位, 避免挂起触发 WDT
    extern void boot_reset_immediately(int reason, int flag);
    boot_reset_immediately(4 /*EXCEPTION*/, 0);
}
```

| 修复 | 内容 |

  → 拿 A包的 PC/RA/EXCVADDR 翻译成函数名定位

## 9. xt-clang 编译成功(2026-09-30,H包)

### 完整编译流程(已验证)

```bash
docker run --rm --platform linux/amd64 \
  --mac-address 00:15:5d:2b:42:e6 \
  -v <sdk>:/work -v <wqcore>:/wqcore \
  -w /work/wq-audio/wq-adk/examples/glass \
  wq-build:latest bash -c '
# 1. LSB loader 修复(lmgrd 需要)
ln -sf /lib64/ld-linux-x86-64.so.2 /lib64/ld-lsb-x86-64.so.3
mkdir -p /usr/tmp/.flexlm

# 2. 构造 license server 文件(SERVER/VENDOR + 原始 INCREMENT)
{ echo "SERVER localhost 00155d2b42e6 27000"; echo "VENDOR xtensad";
  cat /wqcore/toolchain/RI-2020.4-linux/XtensaTools/Tools/lic/license.dat; } > /tmp/lic.dat

# 3. 启动 license server
export PATH=/wqcore/licserv/x64_lsb:$PATH
chmod +x /wqcore/licserv/x64_lsb/{lmgrd,xtensad}
lmgrd -c /tmp/lic.dat -l /tmp/lmgrd.log &
sleep 4

# 4. 编译
export LM_LICENSE_FILE=27000@localhost
export WQCORE_TOOLCHAIN_PATH=/wqcore/toolchain
scons --defconfig=config/7036AC/defconfig.silero && scons -j16'
```

### 关键要点

| 步骤 | 为什么必须 |
|---|---|
| Docker `--mac-address 00:15:5d:2b:42:e6` | license HOSTID 检查(容器 MAC 必须匹配) |
| 方案商的 XtensaTools(不是公开版) | 虽然二进制 MD5 相同,但注册表/config 不同 |
| lmgrd license server | **核心突破**: lmgrd 做 feature 名映射(XTENSA_XCC_TIE→XT_XCC_TIE_EB043600) |
| `LM_LICENSE_FILE=27000@localhost` | 客户端连接 license server(不是直接读文件) |
| `CONFIG_XT_TOOLCHAIN_XT_CLANG=y` | 用 xt-clang(不是 xt-xcc — 后者会报 dangerous relocation) |
| 核配置 params 路径修正 | 方案商的路径是 /opt/xtensa/...,需改成 /wqcore/... |

## 10. H/I 包上板实测与 J 包(2026-09-30 晚)

### H 包实测(COM9 日志 17:39,板上确认是 xt-clang 构建)

- backtrace 在 xt-clang acore ELF 中精确解析:`iot_rpc_caller_init+0xac → rpc_srv_init+0x194 → app_entry`,铁证日志来自 H 包
- 现象:acore 能启动(ro_cfg_init 日志正常),约 2 秒后 `rpc_service.c:424 Asserted!`(dump param: 0x3434b70c/5),之后 crash 处理中二次异常(寄存器全 ASCII 垃圾)→ 复位循环
- 根因:acore 的 RPC caller init 按名字搜其他核的 IPC 服务端口(`wq_ipc_search_port`,循环重试),**bcore/dcore 的服务一直没注册** → 断言。47 秒内 [B-]/[D-] 日志 0 行
- 对比:G 包(GCC dcore)同时段 [A-]=8926/[B-]=22/[D-]=10979,三核全活(7 秒后 dcore 死于 heap_tlsf,即 GCC 老问题)
- H 构建把 acore/bcore 也重编了(bcore 456KB/490KB 字节差异、acore +16B),疑似 vendor install.sh 改变了 RISC-V 工具链环境 → bcore 死因存疑,需隔离

### I 包实测(17:53 截图): 死路,弃用

- v0.9.2.8 底座 sbl 正常启动(2026-06-16 版),但**连 "Boot from" 都没出现**就 WDT 复位循环
- 根因(分区表对比实证):acore 是 XIP 执行,vma 必须等于 `0x34000000 + lma + 0x20`(flash 缓存窗口)。原厂 v0.9.2.8 acore 链接在 0x341A0020(lma=0x1A0000);I 包把 acore 挪到 lma=0x247000 但没重链,跳到 0x341A0020 时读到的是 **dcore 分区中间的字节**,CPU 执行垃圾 → 静默 WDT
- 结论:**acore/bcore 位置不可移动(除非重编)**,只有 dcore(整段拷贝到 DSP RAM)可以自由换位置

### wpk 镜像格式要点(逆向实证)

- wpk = ZIP + memory_config.json + 各镜像;分区 id: sbl=16/acore=32/bcore=48/dcore=112/ro_cfg=194/bootmap=8
- dcore 镜像头(16B): `magic(0xFACECAFE), sect_num, totallen, entry`;之后**段表项与数据交错**(每段 16B 表项: type/offset/vma/len + 数据)
- dcore 段0 是 XIP 段(vma=0x3412C040=窗口+dcore_lma+0x40,约 785KB),其余段拷贝到 DSP RAM(0x2600xxxx/0x2620xxxx/0x263Exxxx)
- xt-clang 比 GCC 多 1 个 LOAD 段(14 vs 13),格式合法无害
- acore/bcore 镜像无头,烧录工具补 32B 头后 XIP 执行(故 vma 尾巴都是 0x20)

## 11. 🎯 总根因抓到: SDK 打包工具 zfill 丢段表项(2026-09-30 深夜定案)

### J 包实测(18:38)与隔离结论

- J 包(G 底座+xt-clang dcore)现象与 H 包相同: acore 起动→2秒 rpc_service.c:424 断言, [B-]/[D-] 零日志
- bcore 用的是 G 包原版二进制(当晨实测能跑)也不出日志 → 凶手只剩 xt-clang dcore 镜像本身
- xt-run 指令集模拟器跑 xt-clang dcore ELF: 5000 万周期无异常, 持续活跃执行(入口代码与 GCC 版逐字节一致) → 代码没问题, 问题在镜像加载

### 真正的根因(三重实证)

dcore 镜像 = FACECAFE 容器, 段表项与数据**交错**排列, 加载器按 `off+len` 链式定位下一表项:

1. **SDK 打包工具有 bug**(`wqcore/tools/SCons/xtensa_tools.py` combine_sections): cache 段(0x26200000)的对齐补零用 `bytes.zfill()` 处理——补的是 ASCII '0' 且把补零长度计入段 len; 而 `off` 跳过补零。→ **len 比 true 内容长 0x58(xt-clang)/0x40(GCC)**, `off+len` 落进下一段的数据区 → 最后一个段表项(.clib.data+.dram.data)被错读成数据 → **DSP 的初始化数据段永远不被加载**
2. **官方镜像全部健康**: v0.7.2.8(14段)/v0.9.2.8(13段)严格链式校验全过、链尾==文件长——其 cache 段 len 不含补零
3. **我们 A-J 全部包的 dcore 都中招**(GCC 版和 xt-clang 版都坏)

### 这个根因统一解释了全部历史现象

| 现象 | 解释 |
|---|---|
| A-G 包(GCC) heap_tlsf 崩溃 | .dram.data(堆/指针表)未加载, dcore 带随机 RAM 跑, 撑几秒后堆损坏 |
| C 包(无 VAD)也崩 | 与 VAD/GCC 无关, 是镜像打包 bug——**"GCC 编 SDK 不兼容"结论作废** |
| H/J 包(xt-clang)零日志秒死 | 烧录后 RAM 状态不同(下载模式用过), 随机数据更致命, dcore 死在日志初始化前 |
| G 包 11:07 会话跑了 7 秒 | 多次复位循环后 RAM 残留数据恰好较友好 |
| rpc_service.c:424 断言 | dcore 没起来 → IPC 服务不注册 → acore 4 秒超时断言(bcore 静默是日志路由依赖问题) |
