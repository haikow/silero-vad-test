# Silero VAD 优化路线图（demo 板线）

> 定位: 链路已跑通（说话 → TVAD → Silero 确认 → 自动录音），本文回答三个问题——
> **怎么稳住不再被看门狗咬**、**功耗怎么实测、用数据选量产方案**、**不涨功耗还能优化什么**。
> 结论先行: 优化主战场在"**Silero 概率怎么被消费**"这一层（状态机/迟滞/复核/调度），
> 不在模型本身。

---

## 一、当前修复路径回顾（到 CCCv5 为止）

| 问题 | 定罪证据 | 修复 | 状态 |
|---|---|---|---|
| 真麦触发不了 | p=0.88 持续 1s 但 `hit:0`；返回值契约——厂商迟滞按**连续调用**计数 | 逐帧平摊最近窗判定 | ✅ 板验（hit:1→录音启动） |
| 开机死机循环 | 3.1s 处 m_ring 断言；持久化 VAD gate 自启 × HIL 独占 dcore 竞态 | 停用 HIL 钩子 | ✅ 板验（零断言） |
| 录音 run too long 贴地运行 | 193 条告警(146 条在录音期, 均值 44ms); v5 降载退出条件被句间停顿踩中 | CCCv6: 降载常驻不退出 + REC_SKIP=6 | ✅ 板验通过(193→10, 仅预热/孤立尖峰) |

**稳定性的铁律**（后续任何功能先过这关）: dcore 20ms 帧预算是硬约束，任何新增计算
上线前用同一指标验收——**窗完成率 ≥95%**（数 [SVs]7-done 行数 ÷ 秒）。这条 Metric
就是"不再被门禁狗咬"的看门人。

## 二、功耗实测方案（先测再选型，回答"本地板子先验证"）

### 现状的一笔功耗债

CCCv2 的 `dfs_request(192M)` 是**无条件持有**（init 后永不释放）→ dcore 常驻 192M，
对应功率图上 ~103mA 恒漏。这是调试期的权宜之计，量产前必须改成会话级。

### CCCv6（功耗版）改法

- `wq_sw_vad_init`（流建立）时持有 192M —— 已有
- 新增 `wq_sw_vad_exit`，在厂商 `sw_vad.c` 的 `sw_vad_remove` 里加一行调用（我们 overlay
  本来就改厂商文件，属可接受侵入；量产若厂商不合入，论证成本也极低）
- 效果: 空闲态回到原厂行为——TVAD 硬件常开（16MHz，微安级），Silero 完全不上电；
  只有候选窗（2s）和录音期才有 192M

### 实测矩阵

| 相位 | CCCv5 现状 | CCCv6 会话级 | 原厂固件对照 |
|---|---|---|---|
| 空闲（无人说话） | 192M 常驻 ~103mA | **TVAD-only ≈ 原厂** | TVAD-only |
| 候选窗（说话头 2s） | 192M | 192M（同） | 原厂 VAD @低频 |
| 录音中 | 192M + 降载 | 192M + 降载（同） | 原厂 VAD + opus |

测法: 两块板（自家台架 GGG / demo 板）+ 功率分析仪，各相位稳态电流 × 日均触发次数
→ 日耗电估算。**空闲相位是决定性的**（时间占比 99%），它追平原厂后，整线功耗即"两段式
门控+按需"方案——表里功耗最低的那档。

### 选型判据

- CCCv6 空闲电流 ≈ 原厂 ±10% → **两段式量产方案成立**，无需第三级前级
- 若仍偏高 → 再谈充电态关 VAD、夜间降灵敏度等策略层省电（零算力成本）

## 三、不涨功耗的优化空间（按优先级，对应实现落点）

外部讨论给的七条方向（9/24 会议纪要）与我们的落点对照——**一半已经天然在手**:

| # | 方向 | 我们的落点 | 现状 | 下一步 |
|---|---|---|---|---|
| 4 | **前级门控，不让 Silero 常开** | **已是两段式**: TVAD 硬件常开 → 2s 候选窗才起 Silero → 录音态再降载 1/3（`REC_SKIP=3`） | ✅ 架构已在（厂商 `CANDIDATE_POWEROPT`） | 只欠 CCCv6 会话级 DFS；这是量产品卖点不是待办 |
| 1 | **调后处理，不调模型** | 阈值 `WQ_SILERO_THRESHOLD`(0.5)；迟滞 = Kconfig `APP_VAD_HIT_CONFIRM_MS`(200ms)/20ms=10 帧确认、35 帧退出 | 单一阈值，无 neg_threshold/最短时长/pad | 库内加官方后处理四件套；**高阈值启动、低阈值保持**双门限 |
| 3 | 误触发冷却+短片段过滤 | 厂商有 record monitor/preroll/prune 地基 | 触发即录、即成文件 | 候选录音复核窗 300-800ms（概率速跌则丢弃）+ 最短时长不成文件 + 连误冷却 |
| 2 | 场景 profile | 充电/佩戴/BLE/包内事件 app 侧都有 | 无 profile 机制 | vad_record gate 加档位: 充电→保守或停、走路→阈值+确认帧提高 |
| 5 | hard negative 轻量特征 | 峰均比/能量斜率/频带比/概率方差，微秒级计算 | 无 | 用真实误触发样本驱动再加，不预先堆 |
| 6 | **真实样本回归** | **已有底子**: MUSAN+LibriSpeech+RIR 的 CI 回归（96 条）+ golden_prob + HIL 工具链 | 文件级判定回归已有 | 补真实负样本（摩擦/拖拽/包内/风噪/电视）；每次调参输出: 误触发/h、人声召回、短句召回、触发延迟 P50/P95、句首保留率、无效录音时长 |
| 7 | **不做清单** | 大模型/多模型并行/常开声纹/云端二次判定/传感器融合常开 | — | 全部与"不涨功耗"冲突，维持不做 |

### 推荐落地顺序

```
CCCv5 板验（链路稳）
→ CCCv6 会话级 DFS + 功耗实测（选型依据）
→ 阈值/双门限 + 候选复核窗（纯状态机, 零功耗）
→ 真实负样本回归集建起来（CI 已有框架, 增量是样本）
→ 按回归结果决定是否加场景 profile / 特征门控
```

一句话: **模型不动，先把"概率的消费方式"调到位**——两段式我们已经有，差的是
后处理状态机和回归集这两块零功耗的肉。

## 四、给方案商的接口（量产谈资）

1. 两段式唤醒已是现成架构（TVAD+GVAD 是他们自家框架），我们只换了 GVAD 内核
2. 需要他们合入的仅 2 处: `sw_vad.c` 加 `wq_sw_vad_exit` 调用（一行，会话级功耗）；
   `aud_sv_vad.c` 的 -Werror 修复（已在我们 overlay）
3. 回归集共建: 我们出 Silero 侧工具链与金标，他们出真机误触发样本

### 原厂 VAD 采样率解剖(2026-10-16, libwq_sw_vad.a 未剥离 debug_info)

- **流配置: 16k**(日志 `[aud_res][mic] sp 16000` / `[VAD] stream create sample_rate:16000`)
- **厂商 wrapper 喂 WebRTC fs=16000**(wq_sw_vad.o 常量扫描: LE u32 16000×1, 8000×0)
- **WebRTC 内部特征在 8k 域**(库含 WebRtcSpl_State48khzTo8khz + S_48_24/S_24_16/S_16_8 级联半带; GMM 6 频带只覆盖 0-4kHz)
- 库本体=标准 WebRTC VAD, 厂商壳加了 tvad_wake_flag/over_hang_max_1/2(hangover)/first_tvad_wake_count 状态机
- **结论: 原厂"消费域"本就是 8k——人声关键信息(基频+前两共振峰)全在 4k 以下, 原厂 16k 输入也是丢掉 4k 以上再判定。Silero 8k 化信息域与原厂等价, 理论不丢检测所需信息 → B4 从"待定"升级"推荐"**
| C1 | 双门限(进入 0.5/0.6, 维持 0.35-0.4)防句中掉字断录 | 长说话不断录; MUSAN 回归误触发不升 | 可与 B 并行 |
| C2 | 回归集补真实负样本(摩擦/包内/碰撞); 每次调参出六项指标 | 基线数据表建立 | 素材并行收集 |
| C3 | 场景 profile(充电保守/关, 走路提高确认帧) | 分场景验收 | C2 数据后 |
| D | hard-negative 特征 / 1x1 自定义内核算力削减 | 按需评估 | 最后 |

**bug 分类备注**(2026-10-16): v5 退出条件属"普通场景实现 bug"(句间停顿是常态而非
特殊场景, 短测试语料掩盖了它); "算力预算紧"本身是结构性约束非 bug, 靠调度管理。
教训入册: 测试用例必须覆盖停顿/断续等真实语音常态模式。
